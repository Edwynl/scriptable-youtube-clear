# Scriptable YouTube Clear

在 iPhone 的 [Scriptable](https://scriptable.app) 里打开 m.youtube.com，并注入一段脚本，让网页版 YouTube 更好用：

- 左侧悬浮面板：搜索 / 返回 / 首页
- 搜索弹窗：实时搜索建议 + 本地最近搜索记录
- 隐藏广告位，自动跳过或快进视频广告，广告后恢复原来的倍速和静音
- 锁屏 / 后台继续播放，锁屏界面和控制中心的媒体控制
- 被微信语音、来电等打断时让出声音，结束后自动继续
- 横屏 = 全屏（和 YouTube App 一样），全屏时最小化自动进入画中画
- 自动点掉“仍在观看？”弹窗
- 偏好 1080p 画质

测试机型：iPhone 14 Pro Max

## 安装

1. 在 Scriptable 里新建脚本，把 `YouTubeClear.js` 的全部内容粘贴进去。
2. 必须在 **App 内运行**：在快捷指令里添加 Scriptable 的 “Run Script” 动作，并打开 **Run In App / 在 App 中运行**，再把快捷指令添加到主屏幕。
   - 不要用普通的扩展模式运行，也不要用快捷指令的小窗 WebView，否则脚本会提示并退出。

## 画中画

iOS 只有在视频处于**原生全屏**时，切到后台才会自动进入画中画；竖屏内联播放时系统不会自动开（这是 WebKit 的限制，网页脚本无法绕过）。所以：

- **横屏**：脚本会可靠地保持全屏，直接最小化即可进入画中画
- **竖屏**：先点 YouTube 播放器的全屏按钮，或把手机转横屏，再最小化
- 需要打开 iPhone 的 **设置 → 通用 → 画中画 → 自动开启画中画**

在横屏时手动退出全屏，这个视频就保持内联（此时最小化不会有画中画）；转回竖屏再横屏，或换一个视频，会重新自动全屏。

没出现画中画时，回到 App 打开调试面板，看最小化那一刻的日志：
- `blur ignored (native player)`：最小化时在全屏里（正常）
- `bg visibilitychange (hidden) mode=…`：进入后台时的模式。`picture-in-picture` 表示画中画已开启；`inline` 表示最小化时不在全屏；`fullscreen` 表示在全屏但系统没有开画中画（检查上面的系统设置）

## 暂停是怎么判断的

脚本要同时做到两件事：**切后台时系统造成的暂停要自动恢复**（后台播放），**用户的暂停要尊重**。难点是 iOS 原生全屏、画中画、拔耳机、来电造成的暂停，网页都收不到触摸事件，看起来和“系统暂停”一样。规则如下：

| 暂停发生时 | 处理 |
|---|---|
| 刚有触摸 / 锁屏控制中心点了暂停 | 用户暂停 |
| 画中画里 | 用户暂停（画中画本来就是后台用的） |
| 原生全屏里，页面在前台 | 先当作用户暂停；1 秒内页面真的进入后台（锁屏）→ 撤销并恢复 |
| 内联播放，页面在前台 | 先当作暂停（拔耳机、来电）；1 秒内进入后台 → 撤销并恢复 |
| 页面已在后台 | 系统暂停 → 自动恢复 |
| YouTube 自己在后台调用 `pause()` | 拦截 |

“1 秒内进入后台就撤销”是为了处理一个时序问题：切后台时，系统的暂停有时比后台事件早到几十毫秒。

## 调试面板

**长按左侧面板的首页键**打开（竖屏时），或在屏幕左上角 1.6 秒内连点 4 下。面板上有“复制日志”和“关闭”按钮。关闭脚本时，日志还会自动保存到 `文件` App → Scriptable → `yt-clear-log.txt`。第一行：

| 字段 | 含义 |
|---|---|
| `mode` | 视频当前模式：`inline` 内联 / `fullscreen` 全屏 / `picture-in-picture` 画中画 |
| `pip` | 这个 WebView 是否支持画中画 |
| `hidden` | 页面是否真的在后台（绕过脚本自己的可见性伪装） |
| `bg` | 脚本是否认为已切到后台 |
| `userPaused` | 是否被记为用户暂停（不会自动恢复） |
| `inAd` | 是否正在播放广告 |
| `keepAlive` | 保活音频是否在运行 |
| `interrupted` | 是否正被别的 App 打断（微信语音、来电） |
| `audio` | AudioContext 状态，打断时为 `interrupted` |

## 版本记录

### v1.8.4：画中画时停掉保活音频

v1.8.3 的真机日志显示，第二条语音时把视频恢复的不是 YouTube，而是 iOS 自己：视频被暂停 0.9 秒后先出现 `playing`，YouTube 的 `play()` 之后才来。两条语音的区别在保活音频：第一条时它被系统打断、不占音频会话；第一条结束后脚本在后台把它重新启动（`audio running`），第二条语音时它一直占着音频会话，iOS 就判断打断很快结束，自动恢复了视频。

- 进入画中画时停掉保活音频（画中画本身就能让视频在后台播放），画中画期间不再启动；离开画中画后恢复
- 只有 AudioContext 回到 `running` 才算打断结束（自己暂停保活时不会误判）
- 日志记录画中画里暂停后是谁、多久把视频恢复的（`PiP resumed …ms after pause by …`）
- 新增 3 个测试场景：47/47 通过

### v1.8.3：画中画里被暂停后，不让 YouTube 自己恢复

真机日志显示：Scriptable 里画中画时页面**读不到后台状态**（`hidden` 一直是 false，也没有后台事件），第二条微信语音开始时音频会话也**没有被标记为打断**。视频被暂停约 0.9 秒后，YouTube 播放器自己调用 `play()` 恢复，把声音抢了回来。

- 画中画里的暂停（微信语音、小窗暂停键）进入“让出”状态：网页发起的 `play()` 一律拦截，只有用户点小窗 / 锁屏的播放键才继续
- 真正的音频打断结束（第一条语音那种情况）仍会自动继续
- 画中画里网页的每次 `play()` 都记日志，调试面板新增 `pipYield`
- 新增 2 个测试场景（按真机日志复现）：44/44 通过

限制：第二条及之后的语音没有“结束”信号，听完后需要点一下画中画小窗的播放键。

### v1.8.2：微信语音期间拦截 YouTube 自己的 play()；调试面板更容易打开

v1.8.1 在真机上仍会抢第二条语音。模拟测试发现两条可能的路径：

- 打断期间 YouTube 播放器自己调用 `play()` 恢复视频（绕过了脚本的所有判断）→ 打断期间、页面在后台时拦截网页发起的 `play()`
- 读不到页面隐藏状态时（只有 blur），“进入后台多久”一直是 0，打断被当成刚切后台 → 加入以第一次后台事件为起点的后备计时

**调试**
- **长按左侧面板的首页键**打开调试面板（左上角连点 4 下也行，改为在 window 捕获阶段监听，不会被 YouTube 顶栏吞掉）
- 调试面板新增“复制日志”“关闭”按钮，显示最近 400 条
- 关闭脚本时自动把日志存到 Scriptable 文件夹：`文件` App → iCloud 云盘（或我的 iPhone）→ Scriptable → `yt-clear-log.txt`
- 后台的每次恢复尝试、网页 `play()` 都会记日志

新增 2 个测试场景：42/42 通过（v1.8.1 40/42）。

### v1.8.1：修复第二条微信语音被抢

第一条语音结束、视频恢复播放时，系统会唤醒后台页面并发出 `resume` / `focus` 事件。v1.8.0 把它当成“回到 App”：清空后台计时、结束打断状态，之后第二条语音开始时的暂停被当成“刚切后台”，立即恢复播放，把声音抢了回来。

- 页面仍在后台时收到的 `resume` / `focus` / `pageshow` 一律忽略
- “进入后台多久”改为在主循环里按页面真实可见性计算，不依赖事件
- 新增 2 个测试场景（连续两条语音，普通后台 / 画中画）：40/40 通过

### v1.8.0：微信语音、来电时让出声音

后台播放时听微信语音会被打断：iOS 暂停视频把声音交给微信，旧版却把它当成“切后台造成的暂停”立刻恢复，保活音频也每 1.5 秒抢一次音频会话。

- 进入后台 1.5 秒后才出现的暂停，视为被别的 App 打断（微信语音、来电、Siri、闹钟），不再恢复播放
- 监听 AudioContext 的 `interrupted` 状态：打断期间保活音频不再抢音频会话
- 打断结束（`interrupted` 解除）或回到 App 时自动继续播放；打断前本来就暂停的不会继续
- 前台来电：通话中暂停，挂断后继续（v1.6.0 起前台系统暂停会一直停着）
- 后台拔耳机没有打断信号，保持暂停，不会外放
- 调试面板新增 `interrupted` 和 `audio`
- 新增 6 个测试场景：38/38 通过（v1.7.1 33/38）

### v1.7.1：修复画中画出现约 1 秒就消失

画中画开始、页面还没进入后台的那一小段时间里，v1.7.0 有三处和 v1.4.0 不同：

- YouTube 自己调用 `pause()` 被当成前台暂停放行（v1.4.0 会拦截）
- 画中画里出现的暂停一律当成用户点的，不再恢复；但“全屏 → 画中画”切换时系统可能暂停一下
- 网页 JS 可以把视频拉出画中画（两个版本都没拦）

**修复**
- 原生全屏 / 画中画里，网页 JS 发起的 `pause()` 一律拦截（用户在这两种模式下点的暂停来自系统控件，不经过网页 JS）
- 进入画中画后 2 秒内出现的暂停当作切换过程造成的，自动恢复；“全屏里暂停，1 秒内变成画中画”也撤销暂停
- 画中画中，没有用户操作时，网页 JS 调用 `webkitSetPresentationMode` / `webkitEnterFullscreen` / `webkitExitFullscreen` / `exitPictureInPicture` 想离开画中画，一律拦截
- 上滑回主屏幕（blur）和离开画中画后 2 秒内，不自动全屏，避免在过渡期插手
- 日志记录播放模式变化时是在播放还是暂停
- 新增 6 个测试场景：32/32 通过（v1.7.0 27/32）

### v1.7.0：修复最小化后没有画中画

v1.4.0 横屏时每 300ms 强制全屏，所以最小化时总在全屏里，能自动画中画。v1.5.0 把它改成“只在转横屏那一下尝试一次”，以下情况就进不了全屏，也就没有画中画：

- 转横屏时视频还没加载好（只试一次，不再重试）
- 先横屏、再打开视频（没有“转屏”这个动作）
- 直播（时长是无限大，被 v1.6.0 从 Codex 版采用的时长检查排除）
- 进过一次画中画后：v1.6.0 从 Codex 版采用的“全屏中”标记可能不会被清掉，之后不再自动全屏

**修复**
- 横屏 = 全屏：在主循环里持续检查，视频没加载好会重试（每个视频最多 3 次），先横屏再开视频也会全屏，直播也算，从画中画回到页面后自动回到全屏
- 保留 v1.5.0 的改进：在横屏时手动退出全屏，这个视频不再被拉回（进入画中画、切后台、转回竖屏都不算手动退出）
- 判断全屏 / 画中画只看视频元素的实时属性，删掉容易过期的标记
- 如果 YouTube 给视频加了 `disablepictureinpicture`，自动去掉
- 调试面板新增 `mode` 和 `pip`；切后台时的日志记下当时的播放模式，方便排查
- 播放页也包括 `/live/` 直播链接

### v1.6.0：合并 Claude v1.5.0 与 Codex v1.5.0

以 Claude 版为基础，吸收 Codex 版的优点，并修复两个版本都有的问题。

**两个版本都有的问题（本版新修）**
- 前台被系统暂停（拔耳机、来电）后，之后一锁屏视频就自己开始播放（外放）
- 监听 `window` 的 blur 用了捕获模式，会收到输入框等元素的失焦，被误判为切后台；还会拦截页面上所有元素的 blur 事件
- `visibilitychange` 在回到前台时也会触发，旧版把它也当成了切后台

**来自 Codex 版**
- 只在真正处于后台时拦截 `pause()`；前台的暂停一律尊重（旧版前台也会拦截）
- 进入全屏时的 blur 不算切后台，全屏开始时重置后台状态
- 锁屏“下一个”只点击一次（旧版会点两次，可能连跳两个视频）
- 每个锁屏动作单独注册，某个动作不被支持时不影响其他动作
- 锁屏进度条随每次循环更新
- 用户暂停后停止保活音频省电（本版改为暂停超过 10 分钟才停，短暂停仍能从锁屏直接继续）
- 广告和 UI 修复合并进一个主循环，去掉单独的 300ms 定时器
- 广告期间不设置画质
- 搜索框：关闭自动大写和拼写检查，外接键盘 Esc 关闭
- 侧边按钮加 `role` 和 `aria-label`，旁白可读
- `'use strict'`、搜索建议空值保护、返回首页的兜底跳转

**保留 Claude 版的做法（Codex 版这几处有问题）**
- 画中画里的暂停当作用户暂停（Codex 版会自动恢复）
- 全屏时锁屏仍然后台续播（Codex 版会停住）
- 横屏自动全屏只在转为横屏时触发一次，只在播放页（Codex 版退出全屏后会被拉回，首页预览视频也会全屏）
- 广告中途切换视频时不重置广告状态（Codex 版会让下个视频停在 16 倍速静音）
- 广告结束只撤销我们设置的 16 倍速，恢复的是正片时的倍速和静音
- “仍在观看？”弹窗按弹窗文字匹配，2 秒检查一次，用 `textContent`
- 原生方法只保存一次、监听器统一登记，`destroy()` 完整还原
- 整页刷新后自动重新注入

**未采用**
- Codex 版开启了锁屏 ±10 秒快退快进：iOS 会因此把锁屏的“上一个 / 下一个”换成 ±10 秒按钮，所以保持关闭
- Codex 版拖动锁屏进度条会同时开始播放：本版暂停中拖动保持暂停

### v1.5.0

修复全屏时无法暂停；横屏全屏只触发一次；强制 HD 不再轮询；广告后恢复静音和倍速；弹窗检测降频；搜索建议丢弃过期结果；`destroy()` 完整还原；整页刷新后自动重新注入。

# YouTube Music 脚本（`music/YouTubeMusicClear.js`）

同样在 Scriptable 里运行，打开 music.youtube.com：隐藏广告、跳过 / 快进广告、后台和锁屏播放、锁屏上一首 / 下一首、把“打开 App”链接改成网页打开、修复列表项点了没反应。安装方法和 YouTube 脚本相同。

## v4.0.4：语音放完后把声音接回来

v4.0.3 的真机日志加上实测反馈：语音放完后系统把音乐恢复成了“播放中”，但 App 在后台时音频会话没能重新激活（保活音频随即变成 `interrupted`），结果是**无声播放**，回到 App 才有声音；而脚本看到“正在播放”，还把保活音频关了，之后再没尝试。

- 系统恢复播放后（只在语音结束之后，不会在语音期间抢），每秒尝试重新激活音频会话一次，最多 30 秒；保活音频进入 `running` 即表示声音回来了（日志 `audio restored after …s`）
- 尝试期间保活音频保持开启；回到 App 时自动结束
- 修复：点列表里的歌曲链接后，脚本还会再补点一次（`tap web link` 之后又出现 `tap fallback` / `spa click`）
- 测试工具支持 `ONLY=关键字` 只跑部分场景、`DEBUG=1` 打印脚本日志
- 新增 2 个测试场景：34/34 通过（v4.0.3 33/34）

## v4.0.3：按真机日志修正“被打断”的判断

v4.0.2 的真机日志显示：
- **语音结束后 iOS 会自己把音乐恢复**（`playing … resumed by system`），语音期间 App 也没有被挂起（心跳日志一直在）
- 但**保活音频在切到后台的那一刻、以及系统刚恢复音乐时，都会被标成 `interrupted`**，而音乐其实还在播放。脚本据此误判为“被别的 App 打断”，停掉了所有恢复手段；之后再出现暂停时不会恢复，也不记日志
- 网页读不到 `navigator.audioSession` 的状态（`state` 为空）

修复：
- 音乐还在播放时，保活音频的 `interrupted` 一律忽略；真正的打断仍由“后台一段时间后出现的暂停”判断，由系统恢复播放来结束
- 前台来电：暂停时保活音频已处于 `interrupted` 才算来电，挂断后自动继续
- 所有暂停都记日志，并注明原因（`pause: …`）
- 点击补点只用于歌曲 / 歌单卡片：v4.0.0 去掉播放进度判断后，点播放页里的普通按钮（喜欢、暂停）450ms 后会被再点一次；现在卡片里的按钮不补点，已经开始播放 / 切歌也不补点
- 新增 5 个测试场景（其中 2 个按真机日志复现）：32/32 通过（v4.0.2 30/32）

## v4.0.2：日志一定拿得到；恢复播放更积极

- **关闭脚本后 Scriptable 直接弹窗**显示本次日志，点“复制日志”复制到剪贴板（不依赖网页，也不怕调试面板打不开）；不需要时把文件开头的 `SHOW_LOG_ON_CLOSE` 改成 `false`
- 运行中每 3 秒把新日志取回 Scriptable 这边保存，关闭后网页取不到也不丢
- 日志文件：iCloud 写不进去时改存本机（文件 App → 我的 iPhone → Scriptable → `yt-music-clear-log.txt`）
- **三根手指同时点屏幕**打开调试面板（左上角连点在 YT Music 里会点到 logo / 菜单）
- 打断结束恢复播放时先把保活音频接回来再播放，多重试一次，3 秒后记录是否真的在播
- 新增外层脚本模拟测试 `music-outer.mjs`（6 项）和三指场景：27/27 通过

## v4.0.1：微信语音结束后自动继续

v4.0.0 能在语音期间让出声音，但语音结束后音乐不会自己继续：后台稳定播放时保活音频已停，没有“打断结束”的信号；没有画中画撑着，iOS 很可能在语音期间把 App 挂起，也就收不到结束通知。

- 接入 iOS 的音频会话状态 `navigator.audioSession`：从 `interrupted` 离开即视为对方交还声音，自动继续播放（事件和 4 秒一次的轮询双保险）
- 恢复时调用 YT Music 自己的 `playVideo`，让播放器界面同步；恢复后 3 秒内不让它自己再暂停
- 打断期间每 4 秒记一行心跳日志（`still interrupted …`），带音频会话和保活音频状态，用来判断语音期间 App 有没有被挂起
- 调试面板新增 `session`；启动日志会记下 `audioSession` 是否支持
- 新增 3 个测试场景：26/26 通过（v4.0.0 24/26）

限制：如果 iOS 在语音期间把 App 挂起，网页里的代码无法运行，只能在语音结束后点锁屏 / 控制中心的播放，或回到 App（会自动继续）。

## v4.0.0：按 YouTube 脚本的经验重写（原版 v3.5.4 在 `music/archive/`）

**听微信语音、来电时让出声音**（原版会抢）
- 在后台待了一会儿才出现的暂停，视为被别的 App 打断：不恢复播放、不让 YT Music 自己 `play()`，把声音让给对方；系统恢复播放、锁屏点播放或回到 App 时再继续
- 保活音频只在需要时运行：前台、刚进后台的 5 秒、切歌间隙、缓冲中、用户暂停后 10 分钟内。后台正常播放时由音乐本身保持会话，不再一直占着音频会话（YouTube 脚本的真机日志证明它会让 iOS 很快把视频恢复、打断语音）
- 前台来电：通话中暂停，挂断后继续

**暂停更准确**
- 拔耳机时停住，之后锁屏也不会外放（原版前台的系统暂停一律被拦下，会继续外放）
- 输入框失焦不再被当成切后台；页面在后台被唤醒时的 `focus` / `resume` 不当成回到 App
- 一首歌播到结尾的暂停不当成打断，自动切下一首不受影响

**其他修复**
- 锁屏“下一首”只切一首（原版点击会触发两次，连跳两首）
- 暂停时点开频道 / 歌单页，音乐不会自己响起来（原版点任何链接都会恢复播放）
- 页面里残留广告容器时，不会把正常歌曲静音、16 倍速并拖到结尾（只有播放器处于广告状态或出现跳过按钮才处理）
- “还在听吗？”弹窗：原版用 CSS 把它隐藏了，脚本自己又看不见它，所以永远点不掉；现在不隐藏，按弹窗文字匹配并自动点掉
- 列表项补点：原版判断“页面有没有反应”时带上了播放进度，播放中永远不会补点；等待时间从 180ms 改为 450ms，减少重复点击
- 启动时的提示框里 `\\n` 显示成字面文字，改成真正的换行

**性能与稳定**
- 页面变化不再立刻跑一遍完整检查（合并成 150ms 一次），也不会让主循环一直处于高频；“打开应用”按钮按文字隐藏改为 2 秒一次、用 `textContent`。页面频繁变化时，2 秒内的 DOM 查询从约 3200 次降到约 190 次
- 阻止 YT Music 注册 `visibilitychange` / `blur` 监听（和 YouTube 脚本一致）
- 锁屏动作逐个注册，进度条随主循环更新
- 整页刷新后自动重新注入；`destroy()` 完整还原
- 删除不生效的 `location.assign` / `replace` 改写（WebKit 里不可改写）

**调试**：三根手指同时点屏幕（或左上角连点 4 下）打开调试面板；关闭脚本后 Scriptable 会弹窗提供“复制日志”，日志也存到 `文件` App → Scriptable → `yt-music-clear-log.txt`。
